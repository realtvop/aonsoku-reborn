# Aonsoku 跨设备协调服务设计

日期：2026-06-20

状态：已批准，待实现规划
范围：Rust 协调服务、Aonsoku Web/Electron/iOS/Android 客户端集成

## 1. 背景

Aonsoku 当前具有以下相关能力：

- 本地播放历史由 `playHistory.store.ts` 保存，歌曲累计实际播放 10 秒后加入历史。
- Navidrome/Subsonic scrobble 独立上报，用于服务端播放统计。
- Web/Electron 使用 HTMLAudioElement 播放后端，iOS/Android 使用原生播放后端和原生队列控制器。
- Electron 已有局域网 WebSocket 远程控制，但它以 Electron 为服务端，不支持互联网、多设备身份、离线快照或原子 handoff。

本设计增加一个独立 Rust 协调服务，使同一 Navidrome 用户绑定的 Aonsoku 设备能够同步 Aonsoku 播放历史、观察和控制其他在线设备，并在设备间接续播放。

## 2. 目标

### 2.1 功能目标

1. 同步 Aonsoku 最近播放历史，同时继续向 Navidrome 正常 scrobble。
2. 同一账号允许多台设备独立播放；只有显式 handoff 才转移某个播放会话。
3. B 可以实时查看 A 的歌曲、播放状态和进度。
4. B 可以使用自己的本机 Navidrome 曲库界面控制 A，包括播放内容、队列、进度、随机、循环、音量和收藏。
5. B 可以接续 A 的当前歌曲、进度、队列位置、用户队列、随机和循环状态。
6. A 在线期间快照始终可接力；A 下线后最后确认快照保留 8 小时。
7. 在线 handoff 在 A 暂停后才允许 B 开始播放，并处理并发接管。
8. iOS/Android 在后台播放期间维持原生协调连接。
9. 每台设备使用当前客户端已有的 Navidrome 登录凭据独立绑定，可命名、查看和撤销。
10. 同时支持轻量自托管和多租户公有部署；客户端不内置默认协调服务地址。

### 2.2 成功标准

- 在线状态观察误差不超过 1 秒。
- 正常网络下远程命令端到端 p95 小于 500 毫秒。
- B 完成媒体预加载后，在线 handoff 从 A 暂停到 B 开始播放不超过 2 秒。
- 同一次播放跨 handoff 只生成一条 Aonsoku 历史记录，且最多一次完成态 Navidrome scrobble。
- 断线、重复消息、服务重启和并发接管不会执行过期命令或产生双重 handoff 所有权。
- 协调服务不可用时，本机播放、队列、缓存和 Navidrome scrobble 不受影响。
- SQLite 单实例基准至少支持 1000 个并发空闲设备连接，并记录 CPU、内存和数据库写入情况。

## 3. 非目标

首版明确不包含：

- 播客和网络电台的历史同步、远程控制或 handoff。
- 媒体文件、封面或歌词代理；媒体始终由各设备直接访问自己的 Navidrome 地址。
- 远程渲染 A 的曲库界面或远程操作 Aonsoku 整个 UI。
- 不同 Navidrome 实例或不同用户之间的共享、控制和 handoff。
- 自动抢占其他设备；本机开始播放不会自动停止其他设备。
- 替代 Navidrome scrobble 或修正 Navidrome 自身的播放统计。
- 端到端加密、零知识 Navidrome 身份证明或不信任协调服务的威胁模型。
- PostgreSQL、多实例高可用或跨区域部署。公有部署首版是多租户、单实例 SQLite 服务。
- 重写或合并现有 Electron LAN Control。它继续作为独立的局域网功能存在。

## 4. 已选择的方案

采用“服务端权威会话”模型。协调服务维护设备在线状态、最后播放快照、会话世代和 handoff 事务。实时状态与命令通过 WebSocket 传输；身份、设备管理和历史同步通过 HTTP API 完成。

未采用以下方案：

- 轻量消息中继：服务端更简单，但客户端很难可靠解决断线重连、重复命令、并发接管和旧设备恢复。
- 全量事件溯源：审计能力强，但把每个播放器状态都建模为不可变事件对首版过度复杂。历史同步仍使用轻量事件日志。

## 5. 总体架构

### 5.1 Rust 协调服务

仓库新增独立目录 `coordination-server/`。服务采用 Tokio、Axum、Serde 和 SQLx SQLite，TLS 默认由 Caddy、Nginx 或其他反向代理终止。

服务按职责拆分为以下模块：

- `identity`：身份识别 URL 标准化、Subsonic 凭据验证、账号查找键生成和 SSRF 防护。
- `devices`：设备注册、名称、令牌轮换、撤销、在线状态和同步游标。
- `realtime`：WebSocket 连接、心跳、消息确认、序列、能力协商和连接路由。
- `sessions`：播放快照、远程命令路由、会话世代和 handoff 状态机。
- `history`：账号级历史事件、首次导入、删除、清空、修订号和上限裁剪。
- `storage`：SQLite 仓储、事务和迁移，不向业务模块暴露 SQL 细节。
- `observability`：结构化日志、指标、审计事件与敏感信息过滤。

服务公开三类接口：

- HTTP API：认证挑战、设备注册与撤销、令牌刷新、历史增量同步、账号删除。
- WebSocket：设备在线状态、播放快照、控制命令和 handoff 协调。
- 运维接口：`/healthz`、`/readyz` 和受保护的指标端点。

### 5.2 客户端协调层

客户端新增独立协调模块，不让网络状态机散落在 React 组件或播放器动作中。模块包含：

- 认证与安全存储。
- HTTP 客户端和持久化历史 outbox。
- WebSocket 连接、重连、序列与状态投影。
- 设备目录、远程控制上下文和 handoff 编排器。
- 协议消息到统一播放器动作的适配器。

Web/Electron 使用 TypeScript 传输实现。iOS/Android 后台播放使用原生插件维持协调连接，并通过现有 native bridge 与 `PlaybackBackend`、原生队列控制器同步。所有播放命令必须同时覆盖 Web 和原生分支，遵循仓库的多播放栈一致性规则。

现有 Electron LAN Control 的命令映射可以作为行为参考，但新协调协议必须独立版本化，不能直接复用其无版本消息和认证模型。

## 6. 身份、设备与凭据

### 6.1 用户配置

用户登录 Navidrome 后，在“跨设备”设置页手动填写：

- 协调服务 URL：没有官方默认值。
- 身份识别 URL：默认取当前主服务器 URL，但允许用户修改。

身份识别 URL 必须是协调服务实际验证 Navidrome 凭据的地址。各设备播放媒体时仍可使用自己的内网、外网或备用地址；这些媒体地址不参与账号识别。

身份识别 URL 标准化规则为：

- 协议和主机名转为小写。
- 移除默认端口和末尾斜杠。
- 保留非默认端口和非根路径。
- 禁止用户名密码、查询参数和 URL 片段。
- 不尝试自动发现或合并 URL 别名。

验证请求仍使用用户登录时的原始用户名；账号识别使用去除首尾空白、Unicode NFKC 规范化并转为小写的用户名。账号查找键由服务端稳定密钥对“标准化身份 URL + 规范化用户名”做 HMAC 得到。服务端数据库不需要保存可直接用于日志展示的明文用户名。服务端稳定密钥属于备份的一部分；丢失密钥会使现有账号无法通过身份重新匹配。该规则针对 Navidrome 的用户名语义，不承诺兼容允许仅以大小写区分账号的其他 Subsonic 服务。

### 6.2 使用当前客户端登录凭据

连接时不要求用户再次输入 Navidrome 密码，客户端直接使用当前登录凭据：

- `PASSWORD` 模式：客户端当前持有可还原的 Subsonic `enc:` 凭据，因此可以在本地为协调挑战计算随机盐 token。原始密码不发送给协调服务。
- `TOKEN` 模式：当前客户端只持有固定盐生成的 token，无法产生新随机盐 token，因此发送已有的 `u/t/s` 组合用于验证。
- 原生端应在 Keychain/Keystore 或原生凭据模块内生成或读取证明，尽量不将可还原凭据暴露给 WebView。
- 当前平台无法读取有效凭据时，连接失败并提示用户先重新登录 Navidrome，而不是静默建立未验证设备。

认证流程为：

1. 客户端申请 60 秒有效、只能消费一次的注册挑战。
2. 客户端根据当前认证模式生成或读取 `u/t/s`。
3. 服务端向身份识别 URL 的 `/rest/ping.view` 发起验证。
4. 验证成功后，服务端计算账号查找键、创建或绑定设备，并签发协调服务令牌。
5. `u/t/s` 不落盘、不进入日志，验证完成后立即从请求上下文释放。

Subsonic 的 `t/s` 是可直接重放的 Navidrome 凭据。一次性协调挑战只能阻止协调注册接口被重复提交，不能从密码学上阻止恶意协调服务重放看到的 `t/s`。本设计的安全承诺是“不发送原始密码、可信协调服务不留存证明”，而不是零知识认证。`TOKEN` 模式下的固定 `t/s` 尤其应被视为长期 bearer credential。

### 6.3 协调服务令牌

- HTTP 使用 15 分钟有效的访问令牌。
- 每台设备获得旋转式刷新令牌；数据库只保存其 hash。
- 刷新令牌在连续 90 天未使用后失效，或在设备撤销时立即失效。
- 浏览器 WebSocket 无法可靠附加自定义 Authorization 头，因此客户端先通过 HTTP 获取 30 秒有效、只能使用一次的 WebSocket ticket，再建立连接。
- 原生端将刷新令牌保存在 Keychain/Keystore，Electron 使用安全存储；纯 Web 端保存在 IndexedDB，并在 UI 中说明其 XSS 风险。
- 撤销设备时，服务端废止令牌、关闭现有连接并拒绝后续刷新。

### 6.4 SSRF 与验证请求

公有模式默认：

- 只允许 HTTPS 身份识别 URL。
- 拒绝回环、私网、链路本地、组播和保留地址。
- DNS 解析后固定目标地址，并在每次重定向后重新执行协议、主机和地址检查。
- 限制连接、首字节和总请求超时以及响应体大小。
- 限制重定向次数，不转发任意客户端请求头。

自托管管理员可以通过显式配置允许 HTTP 和私网地址。该开关默认关闭，并在文档中标记其信任影响。

注册、刷新和验证接口均有按来源、身份和账号的速率限制。认证参数必须在 HTTP 访问日志、错误、追踪和 panic 输出中统一脱敏。

## 7. 核心数据模型

### 7.1 Account

- 随机账号 ID。
- HMAC 账号查找键。
- 账号级历史上限，默认 100，允许范围 1–1000。
- 当前历史世代和最新历史修订号。
- 创建、更新时间和删除状态。

### 7.2 Device

- 随机设备 ID、账号 ID。
- 用户可编辑名称、平台、客户端版本和协议能力。
- 创建时间、最后在线时间、撤销时间。
- 历史同步游标和遗留历史是否已导入。
- 刷新令牌 hash 与轮换状态。

### 7.3 PlaybackSession

- 随机播放会话 ID和所属设备。
- 单调递增会话世代。
- 每次接受完整快照时递增的快照修订号。
- 在线、离线或已转移状态。
- 最后确认快照、快照时间和离线时间。
- 已转移到的设备或会话 ID。

播放快照是版本化结构，至少包含：

- 当前歌曲 ID、进度、时长、播放/暂停状态和采样时间。
- 上下文队列、来源 ID/名称、当前位置。
- 用户队列、当前是否位于用户队列及恢复上一首所需的最小历史。
- 随机和循环状态。
- 当前逻辑歌曲播放会话 ID。
- 累计有效播放时间、是否已写入 Aonsoku 历史。
- 是否已发送 Navidrome now-playing 和完成态 scrobble。

服务端验证快照协议、字段范围和大小，但不把歌曲 ID解析为完整媒体对象。B 使用本机元数据缓存或 Navidrome API 恢复歌曲对象。单个快照最多包含 2000 个歌曲 ID，序列化消息最大 512 KiB；超限时返回明确错误，不静默截断。

### 7.4 HistoryEntry 与 HistoryOperation

历史条目包含：

- UUIDv7 事件 ID。
- 历史世代和服务端修订号。
- 逻辑歌曲播放会话 ID。
- 歌曲 ID及离线显示所需的精简歌曲信息。
- 客户端进入历史的时间、最近一次服务端时钟偏移和服务端接收时间。

历史操作包含幂等操作 ID，类型为新增、删除单条、清空或修改上限。单条删除记录 tombstone；清空操作递增账号历史世代，旧世代条目和上传不能复活。

## 8. 播放历史同步

### 8.1 正常记录

保留现有 10 秒规则：歌曲累计实际播放达到 10 秒后加入 Aonsoku 历史。协调历史不替代 Navidrome scrobble。

客户端先把历史操作写入持久化 outbox，再异步上传。服务端以操作 ID和历史事件 ID保证幂等，分配账号级修订号，并按照账号级历史上限裁剪最旧条目。上限变化由服务端串行化，最后被服务端接受的修改生效并同步到所有设备。

正常历史按照经过最近一次服务端时钟偏移校正的播放发生时间排序，并使用服务端修订号作为稳定决胜条件。服务端拒绝明显位于未来的时间，离线期间保留设备内事件顺序。控制命令、会话世代和同步修订仍完全使用服务端顺序，不依赖设备墙上时钟。

远程控制 A 时，只有实际播放的 A 记录播放时间、历史和 scrobble；B 的远程投影不记录本机历史。handoff 时累计播放时间、历史已发送标志、now-playing 标志和 scrobble 标志一并迁移。

### 8.2 首次遗留历史导入

现有历史只有按新到旧排列的 `ISong[]`，没有真实时间、事件 ID或播放会话 ID。每台设备只允许执行一次遗留导入：

1. 第一台连接的设备以现有顺序建立初始服务端序列。
2. 后续设备的旧序列与服务端序列按歌曲 ID做确定性的最长公共子序列匹配。
3. 匹配项视为共同历史；未匹配项按各自相对顺序合并为最短公共超序列。
4. 同分支使用设备创建时间和设备 ID作为稳定决胜顺序。
5. 合并后立即应用账号历史上限，并标记该设备已完成遗留导入。

该算法能合并大部分设备间复制出的共同历史，但无法完美区分旧列表里多次播放的同一首歌。此限制仅影响升级前数据；新事件使用稳定 ID精确去重。

### 8.3 删除、清空与离线设备

- 删除单条历史同步到所有设备，并为事件 ID建立 tombstone。
- 清空历史递增账号历史世代并同步到所有设备。
- 设备重连后先拉取缺失修订，再上传本地 outbox，避免旧状态覆盖新状态。
- tombstone 在所有未撤销设备确认相应修订之前保留。超过 30 天未同步的设备恢复时必须执行服务端全量快照同步，且不得重新提交已完成导入的本地基线。
- 撤销设备不参与 tombstone 回收条件。

## 9. 实时协议与在线状态

### 9.1 消息封装

每条实时消息包含：

- 协议版本、消息类型和唯一消息 ID。
- 连接 ID、源设备 ID和可选目标设备 ID。
- 播放会话 ID、预期会话世代和连接序号。
- 服务端时间以及类型化载荷。

命令必须返回确认或结构化错误。服务端缓存短期消息 ID结果，重复命令返回原结果而不重复执行。

协议由版本化 JSON Schema 和 OpenAPI 文档定义。Rust 与 TypeScript 类型从协议源生成。握手交换协议范围和能力位；历史同步、观察、控制和 handoff 可以按能力分别启用或禁用。

### 9.2 心跳与快照

- 客户端每 15 秒发送心跳。
- 连续 45 秒未收到有效心跳即标记离线。
- 播放、暂停、切歌、拖动、队列、随机或循环变化时立即发布完整快照。
- 正在播放时每 5 秒发布一次基准快照。
- 观察端使用服务端校准时间在本地插值进度，不依赖设备墙上时钟。
- 快照是覆盖状态，不积累离线发送队列；断线期间只保留最新快照，重连后立即发送。
- A 在线时快照始终可接力。A 离线后，最后确认快照从确认时间起保留 8 小时，且进度冻结，不推测离线期间发生的播放。

服务端重启后，客户端重新连接并提交最后接收序号。服务端从 SQLite 恢复设备、会话和最后快照；无法补发的临时在线事件由新的完整状态代替。

## 10. 远程控制

B 选择“控制 A”时：

1. B 暂停自己的本机播放器并进入远程控制上下文，但不转移 A 的播放会话。
2. B 投影 A 的歌曲、队列、状态和插值进度。
3. B 继续使用自己的 Navidrome 曲库和页面。因为账号和身份 URL 相同，歌曲、专辑和歌单 ID被视为一致。
4. 播放歌曲、专辑、歌单或编辑队列时，B 发送媒体 ID和意图，A 在本机获取所需元数据并执行。
5. A 的 Web 或原生统一动作层执行命令并发布新快照。

首版远程能力包括：

- 播放、暂停、上一首、下一首和 seek。
- 播放本机浏览到的歌曲、专辑或歌单。
- 添加、移除、排序和清空队列。
- 随机、循环、音量和收藏。

远程控制命令只发送给在线设备，不做离线排队。多台设备同时控制 A 时，服务端按接收顺序串行路由；每条命令携带预期会话世代，旧世代命令返回 `stale_epoch`。

A 的本机用户始终可以操作播放器。本机动作和远程命令由 A 的动作层串行执行，后发生者生效。B 退出远程控制后保持本机暂停，不自动恢复进入控制模式前的内容。

**控制方独占性**：B 进入远程控制上下文时向服务端发送 `control_session_begin`，服务端将 B 标记为活跃控制方。在 B 控制 A 期间，其他设备对 B 发起的远程控制命令和 handoff 候选请求会被服务端拒绝并返回 `forbidden`。B 退出远程控制时发送 `control_session_end` 清除标记；B 断开连接时服务端自动清除标记。这避免控制方在被控制期间被第三方接管或被并行控制。

## 11. Handoff

### 11.1 在线 handoff

handoff 是服务端权威的两阶段事务：

1. B 请求 A 的候选快照，服务端检查账号、媒体类型、状态、快照有效性和会话世代。
2. B 用本机缓存或 Navidrome API恢复队列元数据，加载当前歌曲并 seek 到候选进度，但暂不播放。
3. B 在 15 秒准备窗口内发送 `target_ready`，携带读取到的 A 会话世代和快照修订号。
4. 服务端确认 A 未发生变化后创建事务，并向 A 发送带预期修订号的 `prepare_relinquish`。
5. A 仅在当前修订仍匹配时进入短暂 relinquish barrier，通过实际 Web 或原生播放后端暂停，提交最终精确快照并确认。此期间 A 的本机用户操作会取消事务，而不是被延迟执行。
6. 服务端在单个 SQLite 事务中 compare-and-swap A 的世代，标记 A 会话已转移，并把同一逻辑播放会话授予 B。
7. 服务端将 B 原有本机会话标记为已取代且不可接力；B 收到提交后的新世代，应用最终快照并开始播放。

不需要 A 的用户确认。同一 A 会话同时只能有一个 handoff 成功；其他事务返回 `handoff_conflict`。handoff 后 A 可以主动开始新的独立播放会话，但不能恢复旧世代。

### 11.2 失败与恢复

- B 预加载失败：事务未提交，A 不受影响。
- B 准备期间 A 的歌曲、队列或状态发生变化：返回 `source_changed`，A 不被暂停，B 可刷新后重试。
- A 在线但 3 秒内未确认暂停：事务失败，B 不开始播放。
- compare-and-swap 失败：事务返回冲突并要求 B刷新设备状态。
- 事务提交后 B 播放失败：会话归 B但保持暂停，UI 提供重试；不自动恢复 A，避免确认丢失造成双端播放。
- 服务在提交前重启：未提交事务作废。
- 服务在提交后重启：SQLite 中的世代和归属为准，B 重连后可恢复已授予但暂停的会话。

### 11.3 离线 handoff

A 离线且最后快照未超过 8 小时时，B 可以使用冻结快照直接接管。服务端推进 A 的会话世代并将会话授予 B。A 恢复连接时必须先与服务端世代对齐，并保持旧会话暂停。

如果 A 只是断网但仍在本地播放，协调服务无法在物理上立即暂停它。UI 必须明确区分“已停止在线设备”和“已接管离线快照”。这是离线 handoff 的固有限制，不能通过协议承诺掩盖。

已转移、超过 8 小时、无歌曲或非歌曲媒体的快照不能 handoff。

## 12. 客户端界面

### 12.1 跨设备设置页

登录后新增“跨设备”页面，包含：

- 手动填写的协调服务 URL。
- 默认取主服务器但可编辑的身份识别 URL。
- “使用当前 Navidrome 账号连接”操作。
- 当前设备名称、连接状态、最后同步时间和诊断错误。
- 已绑定设备列表：名称、平台、在线状态、最后在线时间、改名和撤销。
- 账号级历史最大数量；连接后替代现有本地历史上限来源。
- “断开当前设备”：撤销当前协调设备但保留本地历史和服务端账号。
- “删除协调数据”：二次确认后删除全部协调设备、历史、快照和账号数据，不影响 Navidrome 账号。

### 12.2 设备面板

播放器增加设备入口。每个设备显示：

- 名称、平台、在线或离线状态。
- 当前歌曲和实时/最后确认进度。
- 最后同步时间。
- 在线设备的“控制此设备”和“在本机继续播放”。
- 离线但快照有效设备的“在本机继续播放”。

超时、无歌曲、非歌曲或已转移会话不显示接力操作。本机设备提供“返回本机播放”，用于退出远程控制。

控制远端时，播放器持续显示“正在控制 A”。handoff 显示阶段状态：“正在准备歌曲”→“正在暂停 A”→“正在本机继续”。错误提示区分离线、快照过期、会话冲突、媒体加载失败、权限撤销和协议不兼容。

## 13. 错误处理与降级

- 协调状态与本机播放器状态隔离；任何协调错误都不能阻止本机播放。
- 历史 outbox 使用指数退避和随机抖动重试。
- 实时快照只保留最新版本；远程命令从不离线排队。
- 访问令牌过期时自动刷新；刷新令牌撤销或过期后停止重试并提示重新绑定。
- 版本不兼容时分别禁用不兼容能力，不假装操作成功。
- 所有状态变更验证消息大小、字段范围、账号归属、目标在线状态、会话 ID和世代。
- 服务端时间和修订号决定跨设备顺序，设备时间只用于本地插值。

主要结构化错误码包括：

- `authentication_failed`
- `device_revoked`
- `target_offline`
- `unsupported_media`
- `snapshot_expired`
- `stale_epoch`
- `handoff_conflict`
- `source_changed`
- `source_pause_timeout`
- `payload_too_large`
- `protocol_incompatible`
- `rate_limited`

## 14. SQLite、部署与运维

首版只支持 SQLite：

- 启用 WAL、外键和合理的 busy timeout。
- 所有 handoff 提交、历史修订和令牌轮换使用事务。
- 启动时先执行迁移；迁移失败则 readiness 失败并拒绝业务流量。
- 单实例进程持有 WebSocket 连接路由；首版不支持多个协调实例共享一个数据库。
- 提供容器镜像和单二进制部署方式，数据目录与稳定身份 HMAC 密钥必须持久化。
- 备份流程同时包含 SQLite 一致性快照和服务端稳定密钥。

自托管和公有部署使用同一二进制。公有模式启用严格 URL 验证和更保守的配额；自托管可显式开启私网/HTTP Navidrome 验证。

PostgreSQL 与多实例协调不属于首版。未来若引入，业务模块通过存储与连接路由接口扩展，不改变客户端协议语义。

## 15. 可观测性与隐私

结构化日志和指标允许记录：

- 活跃和空闲连接数、重连次数。
- 命令与 handoff 阶段延迟、结果错误码。
- 历史 outbox 积压、数据库事务延迟和 WAL 大小。
- 协议版本、客户端平台和服务健康状态。

禁止记录：

- Navidrome 用户名、密码、`p`、`t`、`s`。
- 完整身份识别 URL中的敏感信息。
- 歌曲标题、艺人、专辑、队列内容和封面 URL。
- 访问令牌、刷新令牌和 WebSocket ticket。

账号、设备和会话在日志中使用不可逆、部署内稳定的短标识。审计事件记录设备注册、撤销、账号删除和 handoff 结果，但不包含认证证明或媒体内容。

## 16. 测试策略

### 16.1 Rust 服务

- 身份 URL 标准化、账号隔离、HMAC 查找与 SSRF 防护。
- 凭据脱敏，确保错误、追踪和 panic 路径不泄漏认证参数。
- SQLite 全新安装、逐版本迁移、事务回滚、WAL 和重启恢复。
- 历史首次导入、幂等上传、删除、清空世代、游标和上限裁剪。
- 使用可控时钟测试 15/45 秒心跳、8 小时有效期和 90 天令牌失效。
- handoff 状态机的预加载失败、暂停超时、并发竞争、重复消息、提交前后重启和世代冲突。
- 使用两个或更多真实 WebSocket 客户端执行协议集成测试。
- 基准测试 1000 个空闲连接以及播放快照写入负载。

### 16.2 TypeScript 客户端

- 认证模式选择、当前凭据证明、令牌存储与撤销。
- 协调状态机、历史 outbox、重连退避和增量同步。
- 远程状态投影、进度插值和命令确认。
- Web 播放后端与 Web 队列控制器的控制和 handoff。
- 设置页、设备面板、远程控制标识和错误状态组件测试。
- 协调服务完全不可用时的播放、历史与 scrobble 回归测试。

### 16.3 原生客户端

- iOS 和 Android 原生连接在前台、后台播放和恢复场景下的生命周期。
- 原生播放器与原生队列控制器接收远程命令和应用 handoff 快照。
- 设备断网后恢复时，旧世代会话保持暂停。
- 原生凭据模块不会把可还原凭据写入日志或普通 Web 存储。

### 16.4 跨端验收

- Web→Electron、Electron→iOS、iOS→Android 等组合的在线 handoff。
- 离线 7:59:59 可接力，8:00:00 后不可接力。
- A、B、C 同时独立播放，B 只接管 A，C 不受影响。
- B、C 同时接管 A，只有一个事务成功。
- handoff 前后历史事件和 Navidrome scrobble 不重复。
- A 被接管后离线恢复，不会自动播放旧内容。
- 设备撤销后现有连接立即断开，无法刷新或重新控制。

## 17. 迁移与推出

1. 协调服务协议从版本 1 开始，所有消息带显式版本和能力位。
2. 客户端先引入独立协调模块和关闭状态下无行为的设置入口。
3. 本地播放历史从裸 `ISong[]` 升级为带事件 ID、时间和播放会话信息的结构，同时保留一次遗留导入适配器。
4. Web/Electron 完成协议与播放器动作集成后，再接入 iOS/Android 原生后台连接；功能发布前所有运行时必须达到一致能力，不以静默忽略代替实现。
5. 初始发布可由客户端显式开关控制，但服务端协议和数据库迁移必须按生产标准处理。
6. PostgreSQL、多实例和更多媒体类型在独立后续设计中讨论，不扩大本规格的实现范围。

## 18. 关键约束总结

- 协调服务 URL由用户手动提供，没有默认官方地址。
- 身份识别 URL可自定义，但必须是协调服务实际验证凭据的可达 Navidrome URL。
- 每台设备独立使用当前客户端登录凭据绑定，无需其他设备配对或确认。
- 同一账号允许多个独立播放会话；handoff 只影响明确选择的源设备。
- 首版只支持歌曲。
- 历史是账号级数据，新增、删除、清空和上限均跨设备同步。
- 在线 handoff 必须收到 A 的实际暂停确认；离线 handoff 无法保证断网但仍播放的 A立即停止。
- A 在线时快照一直有效；离线快照精确保留 8 小时且不推算进度。
- 首版存储只支持 SQLite 单实例，但服务数据模型必须支持多租户。
